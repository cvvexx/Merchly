# Запуск и эксплуатация

Операционная документация Merchly: развёртывание, режим разработки, состав демо-данных
и типовые проблемы. Обзор архитектуры и принятых решений — в [README](../README.md).

## Требования

Только Docker с плагином Compose. Сборка модулей происходит внутри образов
(multi-stage Dockerfile, `maven:3.9-eclipse-temurin-17` → `eclipse-temurin:17-jre-alpine`),
поэтому Java и Maven на хосте не нужны.

## Запуск прод-конфигурации

1. Склонируйте репозиторий:
   ```bash
   git clone https://github.com/cvvexx/Merchly.git
   cd Merchly/
   ```
2. Создайте файл окружения из примера — `.env.prod` в git не хранится:

   Linux / macOS:
   ```bash
   cp .env.example .env.prod
   ```
   Windows (cmd):
   ```cmd
   copy .env.example .env.prod
   ```
   Значения по умолчанию годятся только для локального запуска — пароли БД, секреты
   клиентов Keycloak и ключи MinIO лежат в открытом виде.
3. Поднимите стек:
   ```bash
   docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
   ```
4. Дождитесь, пока контейнеры станут `healthy`:
   ```bash
   docker compose -f docker-compose.prod.yml ps
   ```
   `frontend-service` стартует последним — он ждёт готовности всех остальных.
5. Откройте:
    * приложение — http://localhost:8080
    * консоль Keycloak — http://localhost:8090 (`admin` / `admin`)
    * консоль MinIO — http://localhost:9001 (ключи из `.env.prod`)

Остановить стек и удалить тома (сотрёт БД, кеш и файлы MinIO):

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml down -v
```

> ⚠️ **Флаг `--env-file .env.prod` обязателен.** Директива `env_file:` пробрасывает
> переменные только внутрь контейнеров, а сам YAML подставляет `${USERS_DB_NAME}`,
> `${MINIO_ACCESS_KEY}` и прочее на этапе чтения файла — для этого Compose по
> умолчанию ищет `.env` в корне проекта. Без флага такие переменные окажутся
> пустыми и часть сервисов не поднимется.

## Порты

| Компонент          | Порт                                                                |
|--------------------|---------------------------------------------------------------------|
| `frontend-service` | 8080 (единственный сервис, проброшенный наружу)                     |
| `product-service`  | 8081 — только внутри сети Compose                                   |
| `user-service`     | 8082 — только внутри сети Compose                                   |
| `review-service`   | 8083 — только внутри сети Compose                                   |
| `order-service`    | 8084 — только внутри сети Compose                                   |
| Keycloak           | 8090                                                                |
| Redis              | 6379                                                                |
| Kafka              | 9092                                                                |
| MinIO              | 9000, консоль 9001                                                  |
| PostgreSQL         | 5432 users, 5433 products, 5434 keycloak, 5435 reviews, 5436 orders |

Swagger UI `order-service` открывается только при локальном запуске сервиса из IDE —
http://localhost:8084/swagger-ui.html — потому что наружу его порт не проброшен.

## Режим разработки

`docker-compose.dev.yml` поднимает только инфраструктуру — БД, Redis, Kafka, Keycloak
и MinIO — а Spring-сервисы запускаются из IDE с профилем `dev`
(`SPRING_PROFILES_ACTIVE=dev`):

```bash
docker compose --env-file .env.dev -f docker-compose.dev.yml up -d
```

Два отличия от прод-конфигурации, о которых стоит знать заранее:

* Keycloak стартует **без** `--import-realm`, реалм `merchly` придётся импортировать
  вручную из `.keycloak/realm-export.json` через консоль администратора;
* бакеты MinIO не создаются и демо-данные не заливаются — контейнера `minio-init` в
  dev-конфигурации нет, а `SPRING_FLYWAY_LOCATIONS` не включает `classpath:db/seed`.

## Демо-данные

В прод-конфигурации стек поднимается с уже наполненным каталогом: **8 товаров** трёх
авторов, **17 отзывов** и **6 пользователей**. Пароль у всех демо-аккаунтов — `demo1234`.

| Логин         | Роль    | Что показывает                                                   |
|---------------|---------|------------------------------------------------------------------|
| `ink_studio`  | `ADMIN` | Управление каталогом и модерация чужих отзывов                   |
| `tirazh_lab`  | `USER`  | Профиль автора с тремя товарами                                  |
| `okhta_press` | `USER`  | Профиль автора; у стикерпака нулевой остаток — «тираж распродан» |
| `kate_v`      | `USER`  | Покупатель, оставил отзывы почти на все товары                   |
| `roman_d`     | `USER`  | Покупатель, среди отзывов есть критические                       |
| `nastya_m`    | `USER`  | Покупатель                                                       |

Регистрация через форму всегда создаёт обычного `USER`. Чтобы посмотреть админский
функционал, войдите под `ink_studio` или выдайте роль `ROLE_ADMIN` вручную в консоли
Keycloak.

### Где что лежит

* пользователи Keycloak — `.keycloak/realm-export.json` (импортируется при первом
  старте контейнера `keycloak`);
* строки в БД — `db/seed/R__seed_demo_*.sql` в `user-service`, `product-service` и
  `review-service`. Они выполняются, только когда задан
  `SPRING_FLYWAY_LOCATIONS=classpath:db/migration,classpath:db/seed` — это делает
  `docker-compose.prod.yml`, поэтому в dev и в тестах сиды не применяются;
* изображения товаров и аватары — `.seed/minio`, их заливает контейнер `minio-init`
  (он же создаёт бакеты `merchly-products` и `merchly-users` и открывает их на чтение).

Идентификаторы демо-записей зафиксированы (`a0000000-…` — пользователи,
`b0000000-…` — товары, `c0000000-…` — отзывы) и связывают четыре независимых
хранилища, поэтому менять их нужно во всех файлах сразу.

### Как получить сиды на уже запущенном окружении

Сиды применяются при первом старте на пустых томах. Чтобы получить их заново,
пересоздайте тома:

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml down -v
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
```

## Кеши

Redis используется и как кеш (`spring.cache.type=redis`, JSON-сериализация), и как
хранилище сессий BFF. Все записи имеют TTL, инвалидация — через `@CacheEvict` в
сервисном слое.

| Сервис            | Кеш                                                    | Что хранит                                           | TTL    |
|-------------------|--------------------------------------------------------|------------------------------------------------------|--------|
| `product-service` | `productList`, `product`                               | список каталога (в т.ч. по фильтру), карточка товара | 10 мин |
| `user-service`    | `userCart`                                             | корзина пользователя                                 | 2 мин  |
| `user-service`    | `private_user_info`, `public_user_info`, `users_owner` | профиль, публичный профиль, автор товара             | 2 мин  |
| `order-service`   | `order`, `userOrder`                                   | заказ и история заказов пользователя                 | 10 мин |
| `review-service`  | `productStats`                                         | средняя оценка и число отзывов                       | 10 мин |

Корзина остаётся персистентной: она лежит в таблице `cart_item` user-service,
Redis только ускоряет чтение.

## Тесты

```bash
mvn test        # юнит-тесты всех модулей
mvn verify      # + интеграционные тесты (*IT.java, нужен запущенный Docker)
```

Версия Testcontainers поднята до 1.21.4: управляемая Spring Boot 3.4.1 версия 1.20.4
не работает с Docker Engine 29+ (проба соединения использует API 1.32).

Те же команды выполняет CI (`.github/workflows/ci.yml`) на каждый push и pull request:
джоба «Сборка и тесты» гоняет `mvn verify` на JDK 17 и складывает отчёты
surefire/failsafe в артефакт `test-reports`, джоба «Сборка образов» проверяет
compose-файлы и собирает образы всех пяти сервисов.

## Типовые проблемы

| Симптом                                                | Причина и решение                                                       |
|--------------------------------------------------------|-------------------------------------------------------------------------|
| Часть контейнеров не стартует, в логах пустые имена БД | Забыт флаг `--env-file` — см. предупреждение выше                       |
| Каталог пустой после запуска                           | Тома не пустые, сиды не применились — `down -v` и поднять заново        |
| В dev-режиме не пускает в приложение                   | Реалм `merchly` не импортирован — залейте `.keycloak/realm-export.json` |
| Интеграционные тесты падают на старте контейнеров      | Старый Testcontainers с Docker Engine 29+ — нужна версия 1.21.4         |
